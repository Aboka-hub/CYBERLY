## 1. Описание проекта

**CYBERLY** — веб-приложение для мониторинга безопасности личного аккаунта. Система отслеживает историю входов пользователя, автоматически рассчитывает уровень риска, управляет платными подписками и защищает аккаунт от брутфорс-атак.

### Зачем это нужно?

Большинство пользователей не знают когда их аккаунт находится под угрозой:
- Кто-то пытается подобрать пароль
- Вход произошёл с незнакомого устройства или страны
- Аккаунт активен в подозрительное время

CYBERLY решает эту проблему — показывает всю активность в реальном времени и автоматически блокирует аккаунт при признаках атаки.

## 2. Архитектура системы

```
Браузер (localhost:4200)
        │
        ▼
Angular 19 (Frontend)
        │  /api/* → proxy
        ▼
Spring Boot 4 (Backend, localhost:8080)
        │
        ▼
PostgreSQL (порт 5567)
```

Проект разделён на два независимых модуля:

| Модуль | Технология | Порт |
|---|---|---|
| Frontend | Angular 19 + SSR | 4200 |
| Backend | Spring Boot 4 | 8080 |
| База данных | PostgreSQL | 5567 |

### Почему монолит, а не микросервисы?

На данном этапе проект — монолит. Это сознательное решение:
- Проще разрабатывать и деплоить
- Нет накладных расходов на межсервисное взаимодействие
- Достаточно для текущего масштаба

При росте нагрузки можно разделить на сервисы: `auth-service`, `activity-service`, `risk-service`.

## 3. Backend

### Технология: Spring Boot 4

**Почему Spring Boot?**
- Промышленный стандарт для Java backend
- Встроенная безопасность (Spring Security)
- Автоматическая работа с базой данных (JPA/Hibernate)
- Быстрый старт без лишней конфигурации

### Структура пакетов (Clean Architecture)

```
cb.empty.cyberly/
├── accounts/          # Пользователи
│   ├── api/           # Контроллеры, DTO
│   ├── app/           # Бизнес-логика (сервисы)
│   ├── domain/        # Сущности (User, Status)
│   └── infra/         # Репозитории (БД)
├── activity/          # История входов
├── risk/              # Риск-анализ
├── subscription/      # Подписки
└── common/            # Общее (Security, Config, Exception)
```

**Почему такая структура?**  
Каждый слой знает только о своём: `api` вызывает `app`, `app` вызывает `domain` и `infra`. Это называется Clean Architecture — изменения в одном слое не ломают другие.

### Модули backend

#### accounts — Управление пользователями
- Регистрация с хешированием пароля (BCrypt)
- Вход с генерацией JWT токена
- Блокировка после 5 неудачных попыток
- Получение профиля текущего пользователя

#### activity — История входов
- Каждый вход/попытка входа записывается в `login_events`
- Хранится: тип события, IP адрес, страна, устройство, время
- Страна определяется автоматически через внешний API (ip-api.com)

#### risk — Риск-анализ
- После каждого входа система пересчитывает уровень риска
- Анализирует: количество неудачных попыток, географию, частоту входов
- Результат сохраняется как `RiskSnapshot` с баллом 0–100

#### subscription — Подписки
- Хранение платных подписок пользователя
- Автоматическая деактивация просроченных (через планировщик `@Scheduled`)
- CRUD операции с проверкой владельца

## 4. Безопасность

### JWT (JSON Web Token)

**Как работает:**
1. Пользователь логинится → backend генерирует JWT токен
2. Токен хранится в `localStorage` на фронтенде
3. Каждый следующий запрос отправляет токен в заголовке: `Authorization: Bearer <token>`
4. Backend проверяет токен через `JwtAuthFilter` при каждом запросе

**Что хранится в токене:**
- `subject` — email пользователя
- `userId` — ID пользователя
- `expiration` — срок действия (24 часа)
- Подпись HMAC-SHA256 секретным ключом

**Почему JWT, а не сессии?**  
JWT — stateless. Сервер не хранит сессии, что позволяет масштабироваться горизонтально.

### Защита от IDOR (Insecure Direct Object Reference)

**Проблема IDOR:** если пользователь с ID=1 запрашивает `/api/risk/2`, он получит чужие данные.

**Решение — `SecurityUtils.requireOwner()`:**
```java
// Вызывается в каждом защищённом контроллере
SecurityUtils.requireOwner(userId); // кидает 403 если userId ≠ текущий пользователь
```

Каждый защищённый эндпоинт проверяет что запрашиваемые данные принадлежат текущему пользователю.

### Блокировка после N неудачных попыток

**Как работает:**
1. Неверный пароль → `user.failedAttempts++`
2. Если `failedAttempts >= 5` → `user.status = BLOCKED`
3. Заблокированный пользователь получает `HTTP 423 Locked`
4. При успешном входе счётчик сбрасывается в 0

**Почему HTTP 423?**  
Стандарт WebDAV — специально означает "ресурс заблокирован". Отличается от 401 (неверные данные) и 403 (нет доступа).

### BCrypt

Пароли хранятся в базе только в зашифрованном виде. BCrypt — адаптивная хеш-функция, устойчивая к атакам перебором. Даже если база утечёт — пароли нельзя расшифровать.

### CORS

Разрешены запросы только с `http://localhost:4200` (или из env переменной `CORS_ORIGINS`). Блокирует запросы с посторонних сайтов.

## 5. База данных

### Таблицы

#### users
| Поле | Тип | Описание |
|---|---|---|
| id | BIGINT PK | Уникальный ID |
| email | VARCHAR UNIQUE | Email пользователя |
| password | VARCHAR | BCrypt хеш пароля |
| status | VARCHAR | ACTIVE / BLOCKED |
| failed_attempts | INTEGER | Счётчик неудачных входов |
| created_at | TIMESTAMP | Дата регистрации |

#### login_events
| Поле | Тип | Описание |
|---|---|---|
| id | BIGINT PK | ID события |
| user_id | BIGINT FK | Ссылка на пользователя |
| type | VARCHAR | LOGIN_SUCCESS / LOGIN_FAILED |
| ip_address | VARCHAR | IP адрес |
| country | VARCHAR | Страна (из ip-api.com) |
| device | VARCHAR | User-Agent браузера |
| created_at | TIMESTAMP | Время события |

#### risk_snapshots
| Поле | Тип | Описание |
|---|---|---|
| id | BIGINT PK | ID снапшота |
| user_id | BIGINT FK | Ссылка на пользователя |
| score | INTEGER | Балл риска 0–100 |
| level | VARCHAR | LOW/MEDIUM/HIGH/CRITICAL |
| reasons | VARCHAR | Причины через `;` |
| calculated_at | TIMESTAMP | Время расчёта |

#### subscriptions
| Поле | Тип | Описание |
|---|---|---|
| id | BIGINT PK | ID подписки |
| user_id | BIGINT FK | Ссылка на пользователя |
| service_name | VARCHAR | Название сервиса |
| amount | DECIMAL | Сумма платежа |
| next_payment_date | DATE | Дата следующего платежа |
| active | BOOLEAN | Активна / Истекла |
| created_at | TIMESTAMP | Дата добавления |

### Почему PostgreSQL?

- Надёжная реляционная СУБД с открытым кодом
- Поддержка сложных запросов и транзакций
- Хорошая интеграция со Spring Data JPA

## 6. Frontend

### Технология: Angular 19

**Почему Angular?**
- Строгая типизация (TypeScript)
- Встроенные инструменты: роутинг, формы, HTTP клиент
- Компонентная архитектура — легко поддерживать
- SSR (Server-Side Rendering) из коробки

### Страницы

| Маршрут | Страница | Что показывает |
|---|---|---|
| `/login` | Вход | Форма логина |
| `/register` | Регистрация | 2-шаговая форма |
| `/dashboard` | Дашборд | Сводка: метрики, риск, подписки, события |
| `/events` | События | Полная история входов с фильтрами |
| `/risk` | Риск | Большой скор, пороги, причины |
| `/profile` | Профиль | Данные аккаунта |
| `/subscriptions` | Подписки | Полное управление подписками |

### Layout (общий макет)

Все авторизованные страницы используют общий `LayoutComponent`:
- Сайдбар с навигацией (активная ссылка подсвечивается автоматически)
- `<router-outlet>` — сюда загружается контент каждой страницы

### Защита маршрутов (AuthGuard)

```
Пользователь открывает /dashboard
        │
        ▼
authGuard проверяет: есть ли токен в localStorage?
        │
   Да ──┼── Нет
        │         │
        ▼         ▼
  Показать     Redirect
  страницу   → /login
```

### HTTP Interceptor

Каждый запрос к backend автоматически получает заголовок с токеном:
```
Authorization: Bearer eyJhbGciOiJIUzI1NiJ9...
```
Реализовано через `authInterceptor` — не нужно добавлять токен вручную в каждом сервисе.

### SSR (Server-Side Rendering)

Авторизованные страницы рендерятся на клиенте (`RenderMode.Client`) — они зависят от `localStorage` который недоступен на сервере. Публичные страницы (`/login`, `/register`) пре-рендерятся на сервере для скорости загрузки.

## 7. API Документация

Все защищённые эндпоинты требуют заголовок:
```
Authorization: Bearer <JWT токен>
```

### Пользователи

| Метод | URL | Auth | Описание |
|---|---|---|---|
| POST | `/api/user/register` | Нет | Регистрация |
| POST | `/api/user/login` | Нет | Вход, возвращает JWT |
| GET | `/api/user/me` | Да | Профиль текущего пользователя |

**Тело запроса — регистрация/вход:**
```json
{
  "email": "user@example.com",
  "password": "mypassword123"
}
```

**Ответ — вход:**
```json
{
  "token": "eyJhbGciOiJIUzI1NiJ9...",
  "userId": 1,
  "email": "user@example.com",
  "status": "ACTIVE",
  "message": "Login successful"
}
```

**Коды ответа — вход:**
| Код | Значение |
|---|---|
| 200 | Успешный вход |
| 401 | Неверный пароль (+ счётчик: "Attempts: 3/5") |
| 423 | Аккаунт заблокирован |

### История входов

| Метод | URL | Описание |
|---|---|---|
| GET | `/api/login-events/{userId}` | Список событий входа |

**Ответ:**
```json
[
  {
    "id": 1,
    "userEmail": "user@example.com",
    "type": "LOGIN_SUCCESS",
    "ipAddress": "192.168.1.1",
    "country": "Kazakhstan",
    "device": "Mozilla/5.0...",
    "createdAt": "2026-04-17T10:30:00"
  }
]
```

### Риск-анализ

| Метод | URL | Описание |
|---|---|---|
| GET | `/api/risk/{userId}` | Последний риск-снапшот |

**Ответ:**
```json
{
  "id": 1,
  "score": 45,
  "level": "MEDIUM",
  "reasons": "Multiple failed attempts;New device detected",
  "calculatedAt": "2026-04-17T10:30:00"
}
```

### Подписки

| Метод | URL | Описание |
|---|---|---|
| GET | `/api/subscriptions/{userId}` | Список подписок |
| POST | `/api/subscriptions/{userId}` | Добавить подписку |
| DELETE | `/api/subscriptions/{userId}/{subId}` | Деактивировать |

**Тело запроса — добавить:**
```json
{
  "serviceName": "Netflix",
  "amount": 9.99,
  "nextPaymentDate": "2026-05-01"
}
```

## 8. CI/CD (GitHub Actions)

При каждом пуше в ветку `main` или `claude/check-code-visibility-eNWPZ` автоматически запускаются два параллельных задания:

### Backend job
1. Checkout кода
2. Установка JDK 17
3. `mvn clean install -DskipTests` — сборка
4. `mvn test` — тесты

### Frontend job
1. Checkout кода
2. Установка Node.js 20
3. `npm ci` — установка зависимостей
4. `npm run build` — сборка

**Зачем CI/CD?**  
Автоматически проверяет что код компилируется после каждого изменения. Ошибки обнаруживаются сразу, а не при деплое.

## 9. Конфигурация

### Переменные окружения

| Переменная | По умолчанию | Описание |
|---|---|---|
| `JWT_SECRET` | `cyberly-secret-key-...` | Секрет для подписи JWT |
| `CORS_ORIGINS` | `http://localhost:4200` | Разрешённые источники |
| `MAX_FAILED_ATTEMPTS` | `5` | Порог блокировки |

### application.yml (основное)
```yaml
server:
  servlet:
    context-path: /api

spring:
  datasource:
    url: jdbc:postgresql://localhost:5567/cyberly_db
  jpa:
    hibernate:
      ddl-auto: update   # авто-обновление схемы БД

jwt:
  secret: ${JWT_SECRET:cyberly-secret-key-...}

app:
  max-failed-attempts: ${MAX_FAILED_ATTEMPTS:5}
```
